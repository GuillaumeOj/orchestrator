### 3.2 Permission policy — FR-1308 (M) — back
1. **Hard-deny list in the core** (`policy::hard`), checked before anything else on every PermissionRequest, every orchestrator tool call through rules, and inside `decide_permission`:
   - **Always denied** (answered deny at once, line "denied <agent>: … · core: <why>"): any file path in the tool input (Read/Edit/Write/NotebookEdit/Glob/Grep paths, WebFetch `file:`) under a credential store (`compile::CREDENTIAL_STORES`) or the app's `state/`; Edit/Write/NotebookEdit outside the agent's worktree and its `extra_write` dirs; a Bash command any segment of which is `git push`, `gh pr create`, `gh pr merge`, or `git merge` / `git push` targeting the project's base or a protected branch (`main`, `master`, the run's integration branch from a specialist).
   - **User only** (the Overwatch may annotate, never decide): anything a `user` rule matches; any `gh` / `git` call that is not read-only (`gh api` with a method other than GET, `git reset --hard`, `git clean`, `git branch -D`, `git checkout -- …`); WebFetch / network to a host outside the agent's `network_allow`; any MCP tool of an external server that writes (Linear, Notion, Figma, Penpot writes: tools not named `get_*` / `list_*` / `search*` / `read*`).
   - The lists are code constants with tests, not user-editable (ADR-011 §5.1); the policy file can add denies and user-only rules, never remove these.
2. **Policy file** (format: api-contract §1): global `<app data>/policy.toml` and per project `<project>/.orchestrator/policy.toml` when the project tracks `.orchestrator/` in git, else `<app data>/projects/<project id>/policy.toml`. Rules: `match` (FR-708 pattern grammar, unchanged: `Tool`, `Tool(spec:*)`, `Tool(spec*)`, `Tool(dir/**)`, exact), optional `role`, optional `agent`, `effect` = `allow` | `deny` | `overwatch` | `user`, optional `id` (shown in lines as "policy: <id>"), `note`. Loaded at start and on change (file watcher, debounced 500 ms); a parse error keeps the last good version and raises an `alert` decision naming the file and line.
3. **Evaluation order** (FR-1308): hard deny (§3.2.1, before anything else, a one-shot allow included) → one-shot allow → policy (global and project merged; most restrictive effect wins across matching rules: `deny` > `user` > `overwatch` > `allow`, as deny > ask > allow today) → **default effect** when nothing matches: `overwatch` for team roles, `user` for solo sessions (two settings; decision D3) → user. Compound Bash keeps today's rule (a prefix rule never matches a compound command; a compound command with no exact rule takes the default effect).
4. **The store's rules become entries of the policy** (FR-1308 "the store's permission rules (FR-708) are entries of it"): at the first start of P4.4, every non-revoked `permission_rules` row is written to the policy file of its scope (project → project file; role and agent → project file with `role` / `agent`) with `id = "r<row id>"`, and the row is marked migrated (migration 14). From then **Always allow** on a card, **Add rule** on a proposal and **Undo** of a rule all write the file (with `toml_edit`, comments and order kept), and `permission_rules` is no longer read. `effect = "ask"` maps to `user`. The FR-709 actor for a policy answer stays `rule:<id>`.
5. **Settings → Permissions** (the existing settings pane section): the files in effect (global, each project's) with **Open in editor** (nvim, FR-1101), the default effects for team roles and for solo sessions, and the hold length (unchanged). No in-app rule editor beyond that (D4).

### 3.3 The Overwatch session — FR-1306 (L) — back
- **One global agent** `overwatch` (fixed id), not attached to a project's worktree. Its working directory is `<app data>/overwatch/<YYYY-MM-DD>/` (a plain directory, not a repo; `Runtime::start_overwatch`, a new path beside `start`). The role is fixed in code (`Role::overwatch()`), not on the team canvas: default model **Sonnet** (setting), effort default, `permission_mode = dontAsk` so it never raises a prompt of its own, `--strict-mcp-config` with only the `orch` server, tools allowed: `Read`, `Glob`, `Grep` on every registered project's main checkout and its worktrees (read-only; credential stores and app `state/` denied), and `mcp__orch__*` Overwatch tools (§3.4). Everything else denied (`Edit`, `Write`, `NotebookEdit`, `Bash`, `WebFetch`, `WebSearch`, `Task`). Its system prompt (`overwatch/role.md`, compiled in) states its authority and limits (ADR-011 §4) and the citation rule (§3.5).
- **Session per working day** (the chat's day, `digest::today`): started **lazily on the first event of the day** (not at app start: a quiet day costs nothing) with a **briefing** the core writes to `briefing.md` in its directory: the attention snapshot (as `world()`), open decisions, the week's plan and usage, the registered projects and their running features with the paths of their feature docs, today's policy files, and the hard-deny list in words. The first turn is "Read briefing.md, then handle these events: …". The next day's first event starts a new session (the previous one is killed, not resumed).
- **Event-driven** (wake scheduler, `overwatch::Scheduler`): the core keeps a queue of **events** (api-contract §2.1). **Blocking** events wake it at once: a permission whose effect is `overwatch`, a question from an agent, a stuck signal (§3.6), a user message, a rule candidate (§3.7). **Batched** events wait up to the batch window (setting, default 30 s) or until a blocking one comes: decisions that wait on the user (gates, user-only permissions, Governor asks) for annotation, outcomes, decisions closed by the user (so it learns what was decided). One turn carries every queued event (pasted, or a file in `messages/` past 900 chars, FR-206). While a turn runs, new events queue for the next turn. After its turn ends with no event queued, the core **suspends** it after an idle grace (setting, default 120 s, so a burst does not respawn it). A suspended Overwatch is resumed (`--resume`) within the day.
- **Slot and tier**: a reserved slot outside the live-agent cap (as the lead's, FR-203: `reserved_slot` true for `overwatch`), never park-suspended or rotated, `Tier::Critical`, `CostClass::Critical` (draws on the reserve). **Pause all and a reached limit hold it** like any agent (the cards still work); the Governor never defers it otherwise.
- **Usage attribution**: its usage is the agent `overwatch` with allocation `overwatch`; the weekly report and the Week planner show an **Overwatch** row (report `by_role` key `overwatch`).
- **Status** (pushed in `now`, api-contract §3.1): `off` (setting disabled) · `asleep` (no session or suspended, nothing queued) · `waking` (spawn or resume in progress, events queued) · `working` (a turn running, n events) · `paused` (Pause all / limit) · `down` (spawn failed, quick exit, login or limit error on its last turn, or two turns in a row past the turn ceiling of 10 min) with the reason. `down` raises no notification; the header shows it with **Restart** (`overwatch_restart`: fresh session with a new briefing). While `down` or `off`, events are dropped except user messages (kept, delivered on restart) and nothing waits on it: permissions whose effect is `overwatch` go straight to the user.
- **Wake latency** (R12): every turn records `overwatch.turn {events, queued_at_ms (oldest), started_at_ms, first_tool_ms, ended_at_ms, resumed|spawned|fresh, cache_warm}` as an event; `orchd overwatch` prints today's turns and the p50 / p90 wake time (oldest event queued → first tool call). Target < 20 s warm (measured, not enforced).
- The Overwatch's own pane can be opened (escape hatch) from the chat header status; it does not appear in Mission control's lanes.

### 3.4 Overwatch tools — FR-1307 (M) — back, api-contract §2.2
`world`, `inspect`, `decide_permission`, `answer_question`, `annotate`, `nudge`, `resume_agent`, `restart_fresh`, `reprioritize`, `propose_rule`, `post`; declared in `orch-mcp` and exposed **only** to the `overwatch` agent (`ORCH_TOOLS`), dispatched by a new `Runtime::overwatch_tool`. It has **no** tool to start sessions, runs or tasks, decide spec / PR / restart gates, change the weekly plan or Pause all, or edit the policy (only propose). Every tool call that acts is audited with actor `overwatch` (FR-709) and becomes a chat line or entry (§3.8). Errors return `{ code, message }` (e.g. `not_allowed` when a call is on the hard-deny or user-only list, `stale` when the decision closed meanwhile, `bad_request`).
- `decide_permission` settles only a `permission` decision whose evaluated effect is `overwatch` and that is still open, within **60 s** of its creation (setting `overwatch.permission_secs`); past that the card waits for the user and the call returns `too_late`. Allow / deny go through `Runtime::decide` with `decided_by = "overwatch"` (the actor becomes a parameter of `decide`; the user path passes `user`).
- `reprioritize(entry, tier)`: Low / Normal / High only (never Critical), and never above the tier of the entry's allocation in the weekly plan; it changes the queue order only (a new `Governor::set_tier`), admission rules unchanged.
- `restart_fresh(agent)` is FR-415's `restart_fresh` with `by = overwatch`; `resume_agent` and `nudge` behave as the lead's tools (`supervise::lead_tool`) for any agent, the nudge delivered as "ORCH: from the Overwatch: …".
- `post(text, thread?)`: a chat `text` entry by `overwatch`, ≤ 2000 chars, markdown; used to answer the user and for short status ("restarted front-2: …" lines are written by the core from the action, not by `post`).

### 3.5 Questions by the Overwatch — FR-1309 (M) — back
- Every open `question` decision is a blocking event. The Overwatch may answer with `answer_question(decision, answers, sources)` (api-contract §2.2) only with **at least one source**; the core checks each: a path (with optional `#section`) that exists under the run's feature dir (`.orchestrator/features/<slug>/`, any file there, `decisions.md` included) or under the project's `docs/`, read on the integration branch's worktree, or `chat:<entry id>` of an earlier decision **answered by the user** (a question reply, a gate note). Else `ungrounded` and nothing is sent.
- The agent receives "ORCH: the Overwatch answered your question (source: api-contract.md §3).\nQuestion: …\nAnswer: …" (same delivery as the user's reply, `deliver_user`). `decided_by = overwatch`. Multi-question decisions need an answer per question.
- Otherwise it **annotates** the card with its recommendation (`annotate`): product, scope, money, security and irreversible calls, and anything it is unsure of (the role prompt says so; the core does not classify). Gates (spec, PR, restart), Governor asks, budget and user-only permissions can only be annotated.
- An annotation is one per decision (a later call replaces it), ≤ 280 chars, optional `recommend` (an action id of the card, e.g. `approve`, `reject`) and `sources`; it is shown on the card (P4.2 notes §8.1) and kept in the card snapshot.

### 3.6 Unsticking — FR-1309 (S) — back
- The FR-411 signals (`supervise::MemberStatus::stuck`) are computed for **every** agent (team members, leads, solo sessions) and sent to the Overwatch as `stuck` events, once per episode (the existing dedupe): leads and solo sessions at once; a team member **after its lead has had 5 min** with the episode still open (the lead keeps receiving it first, D5).
- Startup failures (a `startup` decision, `resume_failed`) and agents parked on an expired hold whose decision got answered but did not resume are `stuck` events too.
- The Overwatch may `nudge`, `resume_agent`, `restart_fresh` or `reprioritize`; it may not kill, suspend, delete or start. Each action is a line (§3.8).

### 3.7 Learned rules — FR-1308 (M) — back
- The core counts, per **kind of call** = (project, role, tool, the decision's `always` pattern, answer allow | deny), the decisions **answered by the user** (Allow once / Deny; Always allow already makes a rule). On the **3rd** (setting, default 3) it emits a blocking `rule_candidate` event with the three decision ids and the suggested rule (`match` = the `always` pattern, scope project, the role if all three share it). The Overwatch calls `propose_rule(match, effect, scope, role?, from[])` (it may widen or narrow `match`; the core refuses a rule that would allow anything on the hard-deny or user-only lists, `not_allowed`). If the Overwatch is `off` / `down`, or makes no proposal for that candidate within its turn, the core posts the suggested rule itself.
- A proposal is a **decision of kind `rule_proposal`** (P4.2 notes §8.5): context = text, the three earlier decisions as links, the rule in mono, the target file; actions **Add rule a** · **Not now r** · **Edit rule ⏎** (opens the target policy file in nvim with the rule appended, commented out, for the user to edit and uncomment). Level 4: it never notifies and is not counted in the badge (it blocks nobody). Never more than one proposal open per kind of call; **Not now** resets the count ("Asking again after 3 more"); a kind of call with two declined proposals is never proposed again (D6).
- **Add rule** writes the file (§3.2.4) and closes the decision with effect "added to <file label>".

### 3.8 Oversight lines and undo — FR-1310 (M) — back + front
- Every decision settled by the Overwatch closes its chat entry with `line.by = overwatch`, `by_detail` = its reason (≤ 60 chars) and the line gains `sources` (api-contract §3.2). Every unsticking action and rule proposal by the Overwatch is a chat entry of kind `action` (new kind, api-contract §3.2) with its line. Nothing it does notifies.
- **Undo** (api-contract §3.3), offered on the line while it still means something, then "Can't be undone: <why>" when expanded:

| Line | Undo does | Available while |
|---|---|---|
| allowed by policy rule `<id>` | revokes the rule (removes it from its file); the call itself already ran | the rule is in the file |
| allowed by the Overwatch | "Tell back-1 the answer changed": deny the next identical call (one-shot deny, 1 h) and deliver "ORCH: the user reversed the Overwatch's approval of `<call>`: don't repeat it; …" | the agent's session is live and its task unchanged (else "back-1 already moved on") |
| denied by the Overwatch | one-shot allow for that exact call + "ORCH: the user overrode the denial of `<call>`: you may retry it." | same |
| answered by the Overwatch | opens a reply field on the line; the user's text is delivered "ORCH: the user corrected the Overwatch's answer to your question: …" | same |
| reprioritized | restores the previous tier | the entry is still queued |
| rule added (proposal) | removes the rule | the rule is in the file |
| nudged / resumed / restarted fresh | — (no undo: "Can't be undone: it already ran") | — |

- Undo is a user action, audited with actor `user` and the undone line's id; the line then reads "· undone 14:03" (muted).

### 3.9 The chat with the Overwatch — FR-1305 (M) — front, back for the commands
- Header: the title becomes **Overwatch** (one string, `ChatColumn.svelte` `TITLE`) with the status slot (§3.3 status; P4.2 notes §8.6 copy, ux to confirm), **Restart** when `down`, a click on the status opens the Overwatch's session over the board.
- **Input** at the foot in place of the P4.3 footer: "Ask the Overwatch…"; ⏎ sends (⇧⏎ newline), ⌘L focuses it; search moves to `/` (and the header button). Sending writes a `user` / `text` entry (`chat_send`, api-contract §3.3) and wakes the Overwatch; while it is waking the entry shows "waking…"; while `down` / `off` the input stays enabled and the entry reads "Sent when the Overwatch is back" (delivered on restart / when turned on).
- Thread: `user` and `overwatch` `text` entries in time order with the cards and lines (D4 of P4.3 kept); the Overwatch's text is rendered markdown with its source links (a doc path opens the rendered doc in the feature pane; `chat:<id>` jumps to that entry).
- Cards: the **annotation** block (P4.2 notes §8.1) with its sources and recommended action highlighted (never pre-selected); the **deciding** marker "Overwatch is deciding… 42 s" while a permission with effect `overwatch` is within its 60 s and the Overwatch is not `off` / `down` (actions stay live; the user can decide first); then "Waiting for you".
- **Lines** by the Overwatch with their sources ("▸ answered front-1: API pagination · from api-contract.md §3") and the undo of §3.8 (`u` on the focused line, or the button when expanded); `action` lines (nudged / resumed / restarted / reprioritized).
- **Rule proposal** card (§3.7) with its three actions and states (added with 5 s undo, not now).
- Notification and badge rules unchanged (§9.6): `deciding` cards are not counted in the badge and do not notify until they wait for the user (the core already counts `waits_on = user` only: a permission with effect `overwatch` has `waits_on = overwatch` during its 60 s, then `user`; this is the change on the core side, api-contract §3.1).
- Settings: an **Overwatch** section (on/off, model, batch window, permission seconds, idle grace, rule threshold) and the Permissions section of §3.2.5.

## 5. Non-functional
- **Nothing waits on the Overwatch** (ADR-011): cards are posted by the core before any event reaches it; a permission waits at most 60 s on it; `off` / `down` / `paused` never block an action. A test kills the Overwatch mid-turn and checks every open card still acts.
- **Safety** (R11): the hard-deny and user-only lists are checked in the core on every path (policy, Overwatch tool, proposal); unit tests for every list entry (including compound Bash, `cd` prefixes, quoted paths, `~` and `$HOME` expansion, symlinks into a credential store); the Overwatch's role cannot write files or run commands (settings test).
- **Cost**: one session per day, started lazily; briefing ≤ 8 k tokens; a turn's event text ≤ 4 k chars (the rest by reference: ids it can `inspect`). Usage visible as the Overwatch row.
- **Latency** (R12): wake time recorded per turn; target < 20 s warm.
- **One source of state**: the UI renders `now` (status, chat entries, decisions with annotation and `waits_on`); it calls `chat_send`, `chat_undo`, `overwatch_restart` and the settings commands only.
- **Accessibility**: the input is labelled; the status is text, not colour only; Overwatch text entries are `article`s in the feed; a new Overwatch text answer to the user is announced through the existing throttled live region.
- **Tests**: `make ci` green. Core: hard deny and user-only lists; policy load / merge / precedence / default effects / parse error alert / migration of store rules / Always allow and Undo writing the file with comments kept; scheduler (blocking vs batched, batch window, one turn in flight, idle suspend, day rollover, lazy start, down and restart, paused); each tool (allowed, refused, too_late, stale, ungrounded); stuck routing (lead first, 5 min); rule candidates (3rd identical answer, Not now reset, two declines); undo of each line kind; usage attribution; the e2e of §1 (a). UI: status states, input in every status, deciding countdown and hand-over to the user, annotation with sources, Overwatch lines with undo and the undone state, rule proposal states, `/` search and ⌘L input, text entries rendered with links. Tests hold at any date, hour and time zone.

## 6. Acceptance (demo at the PR gate)

6. Kill the Overwatch's process: the header says down with Restart; every card still acts; permissions go straight to the user.
7. `orchd overwatch` shows today's turns and wake times.
