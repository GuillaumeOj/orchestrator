# Fix Icon Build — spec

## Problem

PR #68 added the Liquid Glass app icon (`crates/orch-app/icons/Orchestrator.icon`, Icon Composer
format). Compiling it with `actool` fails on CI with "attempt to insert nil object" (in the
icon-composer item selection), but works on the user's Mac. The workaround now on `main`
(commit 50c037c8) is a **compiled `icons/Assets.car` committed to git**. Tauri bundles it through
`tauri.bundle.json` → `macOS.files`, and `Info.plist` sets `CFBundleIconName`.

That binary goes stale whenever the `.icon` changes, and someone has to remember to rebuild it by
hand on a Mac with Xcode 26+ (the README has the command). The user wants CI to build the icon
from source.

## Root cause (what we know)

| | Local (works) | CI attempts (failed) |
|---|---|---|
| Runner / OS | macOS 27.0.1 | `macos-latest` = **macOS 15** image |
| Xcode / actool | Xcode 27.2 (27B52) | default Xcode 16.4; later `Xcode_26.3` picked by hand (PR #68) |

The `macos-latest` label appears to still point to the macOS 15 image: Xcode 16.4 is its
default, and PR #68 had to pick `Xcode_26*` by hand. On that image, Xcode 26.x is installed but
runs on a macOS 15 host. Our hypothesis (not yet verified on CI): compiling a `.icon` (Liquid
Glass) renders the layers with system frameworks that only ship with macOS 26 and later, so on an
older host actool finds no rendered item and crashes with the nil-object error. The `macos-26`
image (macOS 26.7) ships Xcode 26.6 as its default.

Main hypothesis: **build the app on the `macos-26` image** (Xcode 26.6 on macOS 26) and the
`.icon` compiles. A second, smaller risk: the `.icon` was saved by Icon Composer 27 and uses
something actool 26 can't read. Commit 80e24d68 already cut `icon.json` down to the Icon Composer
26 keys, so this is less likely (see Risks).

## Goal

The app's icon is compiled from `Orchestrator.icon` on every build, locally and on CI. No compiled
icon is kept in git.

## Requirements

1. **CI runner.** The macOS jobs that build the app (`app` and `app-pr` in
   `.github/workflows/ci.yml`) run on `macos-26`, a pinned image rather than `macos-latest`. The
   Rust lint/test macOS job may move too, for consistency, if it costs nothing. `build-app`
   prints `xcodebuild -version` and `sw_vers` so a failure can be diagnosed from the log.
2. **Compile step in `scripts/app.sh build`.** Before `tauri build`, compile
   `crates/orch-app/icons/Orchestrator.icon` with `xcrun actool`. Use the command from
   `icons/README.md`: copy it as `Icon.icon` and pass `--app-icon Icon`, so `CFBundleIconName`
   stays `Icon`. Write the output to a gitignored path under `crates/orch-app/bundle/` (for
   example `bundle/icons/Assets.car`). `tauri.bundle.json` `macOS.files` points to that path.
   - If actool fails or writes no `Assets.car`, the build **fails** and prints actool's output
     (never a silent build without an icon), plus a one-line hint (Xcode ≥ 26 on macOS ≥ 26).
3. **Remove the committed binary.** Delete `crates/orch-app/icons/Assets.car` from git. Keep
   `Info.plist` (`CFBundleIconName`), the classic `icon.png` → `.icns` path (older macOS), and
   the `liquid-glass/` sources.
4. **Post-build check.** After `tauri build`, `scripts/app.sh build` checks that the bundle has
   `Contents/Resources/Assets.car` and that `Contents/Info.plist` has `CFBundleIconName = Icon`.
   If either is missing, it exits non-zero.
5. **Docs.** Update `crates/orch-app/icons/README.md` and the `Info.plist` comment: the icon is
   compiled at build time, the toolchain needs Xcode 26+ on macOS 26+, and nothing has to be
   regenerated by hand. Update `docs/app/RUNNING.md` if it lists build requirements.
6. **Local builds keep working.** Xcode 27 / macOS 27 (the user's Mac) builds and installs with
   `scripts/app.sh install`, and the installed app shows the Liquid Glass icon.

## Out of scope

- Redesigning the icon or changing `icon.json` (unless needed as the fallback below).
- Signing, notarization, or the update channel.
- UI (`ui/`) changes: the frontend node has no work in this feature.

## Acceptance

- `git ls-files crates/orch-app/icons/Assets.car` is empty on the branch.
- The PR's CI is green, including **"Build the app for the pull request"** (`app-pr`). Its log
  shows the actool step compiling `Orchestrator.icon` on macOS 26 / Xcode 26.x.
- The `pr-build` artifact's `Orchestrator.app` contains `Contents/Resources/Assets.car`, and its
  `Info.plist` has `CFBundleIconName = Icon`.
- A local `scripts/app.sh build` passes on the user's Mac. The user confirms the Dock icon on the
  PR build or the local install.

Only the PR's CI can prove the fix: no macOS 26 runner is available before the PR is open. The
lead opens the PR once the task is merged, and CI judges it.

## Risks and fallback

- **actool 26.6 on macOS 26 still crashes.** Then the `.icon` itself probably needs Icon
  Composer 27. Options, in order: (a) use a `macos-26` image Xcode 27 if one shows up
  (`Xcode_27*.app`), (b) re-save the `.icon` in Icon Composer 26 (the user's call, since it touches
  the design), (c) keep the committed `Assets.car` and add a CI check that it is up to date.
  The lead asks the user before choosing (b) or (c).
- **macOS 26 runner capacity.** The `macos-26` image may queue longer. That is accepted.
