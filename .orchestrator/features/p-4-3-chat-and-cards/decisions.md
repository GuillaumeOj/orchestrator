# P4.3 — Decisions

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-11-02 | **No chat input and no Overwatch status in P4.3 code.** The column holds the core's entries only (cards, lines, morning line, digest); the footer says the Overwatch comes later, and ⌘L focuses the chat's search. The store and contract already take `overwatch` / `user` authors and the P4.4 entry kinds. | The Overwatch is P4.4 (FR-1306): a message box that wakes nothing would be a dead surface (same reasoning as P4.2 D2). |
| D2 | 2026-11-02 | The chat log is a **core table** of entries, one per decision (plus the morning line), with the closed decision's **line and card snapshot** written at close. | Decisions leave `now` 10 min after closing, synthesized ones have no row, and older days must stay readable and searchable (FR-1305). |
| D3 | 2026-11-02 | Permissions settled by a store rule, in the pane or by expiry are posted as **lines**, never as open cards, and never notify. | J5 · 2 and §9.6: what is settled without the user appears collapsed; oversight starts before the Overwatch exists. |
| D4 | 2026-11-02 | The thread is **chronological**; a follow-up decision of the same run shows a reference to the earlier one ("↳ after: …") rather than being moved under it. ux may revise in the design pass. | A thread that reorders under the user's eyes breaks `j/k`; the reference keeps "the follow-up sits under the earlier answer" readable. |
| D5 | 2026-11-02 | The chat column is a **fixed column** of the shell, not a pane type; below 1728 the Inspector overlays its slot, docked ≥ 1728 (P4.2 notes §4). | SPEC §9.1 · 4 "the chat a fixed column"; P4.2 F7 measured the centre's minimum width. |
| D6 | 2026-11-02 | The Inbox's level filters (All / Blocking / Errors / Budget) move to the chat header and filter **cards only**; the per-project and per-agent filters of FR-707 are not carried over (Mission control filters by project). | Lines and the digest are history; the badge must never depend on a filter. |
| D7 | 2026-11-02 | Notification click: a real click callback if the macOS plugin offers one; otherwise app activation within 60 s of a notification focuses its card. Back checks first (plan). | tauri-plugin-notification on desktop may not report clicks; the fallback still meets "a notification click opens the app on that card". |
| D8 | 2026-11-02 | ux findings on T-78 (docs/design/p4-3-design-notes.md §0): **F1** a decision open across midnight gets a new entry in the new day (data fix, `continued_from` / `continued_to`), not a UI-only rule; **F2** past 5 open cards the *newer* fold, the 5 oldest stay (supersedes P4.2 §8.3); **F3** SPEC §9.2 / FR-210 wording by lead, agent-facing strings (§11.3) by back; **F4** cleared digest copy "5 done today, all seen"; **F5** all-zero morning line; **F6** the column stays fixed in P4.3 (a hide command is a P4.4 candidate); **F7** notification copy §8.3; **F8** self-clearing synthesized decisions close as `dismissed · core · stale`; **F9** search also matches verb, rule label and open decisions; **F10** an expired permission hold parks and stays a card. Also from the notes: dismiss has no undo in P4.3; a collapsed card keeps its place in the thread. | F1: the core owns state (§9.1 · 10) and keeps every day's thread self-contained for `chat_day`; the rest as argued in the notes. |
| D9 | 2026-11-03 | T-80 leftovers accepted: an ask's `expired` line uses the pump's time, not when the ask cleared; the midnight carry-over is two writes; migration 13 edited in place (unshipped); duplicated SELECT in `events_of_kinds_in`; test clock override on `Now`; perf test asserts the spec's 200 ms in debug. **Follow-ups**: put the lifecycle's final state at the source (stale / expired / decision word) so `line_of` is a plain mapping; batch a pump's chat writes in one transaction. T-81 plan: the D7 fallback (focus within 60 s), no click callback (tauri-plugin-notification 2.4.0 has none on desktop; mac-notification-sys needs a blocked thread per note and the deprecated NSUserNotification API). | Each is rare or outside FR-1305; the fallback is deterministic, testable and keeps `focus_card` the same if a real callback comes later. |
| D10 | 2026-11-03 | T-82 leftovers accepted: the UI keeps composing a line from the live decision until the core's entry arrives (cached; tests and transient pushes need it), `openOutcome` stays per surface, `.pulse`/`.sr` and chat size tokens wait for a tokens pass, `app.now.chat` stays optional, no raw entry storage (≈4 ms per event at 300 entries). **Follow-up**: drop the client-side line composition once the core posts the entry in the same push as the decision (one source for line copy). T-81 follow-up merged: `chat` topic, warn logs on swallowed chat errors. | Within the 16 ms budget and outside FR-1304; the fallback renders the core's `line` whenever it exists. |
